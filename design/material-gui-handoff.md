## Scope and decision

Preserve the existing productive Electron/Lit desktop, its actual domain destinations, local Git workflows, drafts, settings, operation history and validated IPC. Refine the shared visual system and replace proven non-Material interactive anatomy. Do not replace the application with a command catalog, a landing page, or generic forms. Keep the pinned official @material/web 2.5.0 controls. Its presence proves upstream provenance only for the md-* implementations; it does not establish complete Material 3 Expressive conformance.

Local layout/text/surface compositions are legitimate app infrastructure when described accurately. Merely registering a div-based interactive control does not make it a genuine Material control. There is no official Material Web desktop splitter, scrollbar, rich Git diff or draggable grouped document-tab component. Preserve needed behavior and explicitly identify these as application compositions and intentional deviations, rather than inventing upstream provenance.

## Original prioritized findings

1. **High: shared CSS suppresses official component anatomy.** src/renderer/styles.css sets ordinary action buttons to 32px, detail actions to 29px, icon buttons to 34px and notice icons to 26px; button shapes are 6/8px, dialog shape 16px, primary tabs 38px. Core labels fall to 10/11px. The same stylesheet has fixed 38/48/42/27px shell rows. Restore upstream default button/icon/dialog/tab anatomy, using a documented compact mode only where justified and preserving comfortable pointer targets. Grow shell rows with their contents rather than clipping restored controls. Target default button visual height 40px, at least 48px interaction space where feasible, 24px icons, Material label/body roles, and upstream rounded shapes. Do not simply append larger global heights to the existing fixed-grid shell. Measure actual shadow interactive bounds, not only host bounds.
2. **High: searchable choice control is a faux interactive wrapper.** src/renderer/workspace-controls.ts:17 renders div[role=option] with manual keyboard/click behavior. Its absolute-positioned popup can be clipped by ancestors. This feeds workspace preference results. Replace the popup with an official md-dialog containing its isolated mg-search and official md-list/md-list-item selection actions, or use an official select for genuinely small fixed choices. Preserve current-value display, filter isolation, pagination, empty state, supported values, value-change and persistence paths. A searchable dialog is the least risky pattern for this existing API: trigger aria-haspopup=dialog, clear selected indication and action labels, return focus to trigger, scoped Escape, no listbox/option roles layered on button controls. Keep large choices searchable; do not silently convert them to free text. The same file exposes input[type=color] for seed: replace the visible native picker with the existing validated Material text-field path or an official-control color editor, preserving current value and validation.
3. **High: documented primary smoke test is obsolete.** tests/workbench.browser.mjs first waits for .command-list md-list-item and later .explorer, .dock and .document-tabs. These describe the previous command workspace, absent from current app.ts. design/material-provenance.md repeats that obsolete product description and recommends this test. Update both to the current destination navigation, task strip and domain workspaces. Existing tests/material-controls.browser.mjs is a useful live foundation; registration assertions in renderer-contract.test.ts only inspect import/define strings and cannot catch div options, overwritten anatomy or dead controls.
4. **Medium: typography and surface compositions use arbitrary legacy metrics.** components.ts Typography uses 20px/600 title, uppercase 10px eyebrow, 12px muted and hard-coded mint fallback; Surface uses generic bordered cards and arbitrary radius defaults. Map typography to named Material roles with rem-based sizes and line heights; use theme foreground roles and semantic surface-container roles. Avoid outlining every structural panel; reserve borders for genuine separators or outlined cards. Keep code/diff typography as functional data. app.ts:74 sets surface radius to 8px by default; coordinate it with the selected default rather than making CSS ineffective. Respect saved explicit appearance overrides.
5. **Medium: icons and tabs require honest treatment.** workbench.ts:8 contains original SVG paths and workspace-support.ts:36 uses text glyphs for manage, pin and close. Replace visible interface icons with locally bundled official Material Symbols assets with version/license/source recorded, keeping mg-icon API and stable name mapping. Do not rely on a network font. workspace-support.ts composes tabs from md-text-button role=tab in rectangular div borders, not actual Material tabs. Use genuine md-secondary-tab/md-tabs for horizontal navigation if grouped/close/reorder behavior can be retained; otherwise explicitly document and review the advanced document-tab composition, improve its active indicator/shape/targets and correct per-panel aria-controls. Do not destroy grouping, pinning, dock edges, keyboard reorder or dirty-close behavior to obtain nominal component purity. Vertical tab strips are a product-specific composition, not an upstream Material tab claim.
6. **Medium: theme derivation and provenance need precision.** styles.css computes surface container roles with simple color-mix; app.ts uses themeFromSourceColor/applyTheme. Prefer supported Material color-utilities tonal roles for the shared scheme, while retaining existing settings and defaults. Verify light/dark text contrast after changing roles. There is no complete per-surface inventory today, and a package import is not Expressive certification.

## Acceptance and tradeoffs

The deliverable is a coherent Material desktop using genuine official controls for ordinary interaction, an honest composition inventory, working existing tasks, and reproducible built evidence. It must not claim every custom surface is an upstream component, or call ordinary Material Web 2.5.0 full Expressive coverage without a component-by-component assessment. Remaining supported custom desktop compositions and unavailable external states should be explicit. A broad UI rewrite or new features are outside this bounded work.
