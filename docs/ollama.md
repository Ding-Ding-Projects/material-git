# Local Ollama manager

The Utilities workspace independently provides installed models, reviewed local model copies, the official Model Store, reviewed download batches, streamed chat with saved sessions, standalone streaming text generation, a reviewed local-service harness and a bundled offline troubleshooter. Model downloads and official catalog refreshes require explicit actions. Implementation verification never downloads a model or installs third-party software.

## Privileged API and local storage

Documented runtime requests use only `http://127.0.0.1:11434`. The legacy bridge permits version, tags, running models, show, copy and confirmed delete through allowlisted methods and fields. Chat and pull use the durable `localTools` service, streamed NDJSON and bounded polling. Request payloads and response/stream sizes are limited, JSON/UTF-8 errors fail closed, redirects are rejected and a fixed local endpoint prevents renderer-supplied servers.

Catalog, pull journals and saved sessions live under the application's private local tools directory. Durable JSON writes replace an exclusive temporary file atomically. These files are not telemetry or public artifacts. Chat names, system prompts and messages are stored locally as user-requested history. Exports require the explicit chat export action and redact known credential patterns and local path patterns. The export warns that freeform content still requires review; no heuristic can identify every secret.

## Model Store

Refresh reads only the official public library and each family's official tag source at `ollama.com`. It follows recognized page links, retains every recognized published tag and fails the whole new refresh if a family exposes no recognizable tag rows. Each response has a SHA256; the combined response identity, successful timestamp, page/family/variant counts and completeness verdict are recorded. A failed/offline refresh preserves the last complete saved inventory and its last-success timestamp.

Current official pages were inspected read-only: the library lists all families on one page and the sampled tag page lists all tags without pagination. Multi-page behavior is tested with clearly labeled official-page fixtures. Refresh is sequential and bounded to 10,000 pages, 500,000 variants and 8 MiB per page; reaching a bound or changed markup reports incomplete. No curated model suggestions or fabricated installed rows replace the inventory.

Plain text and the adjacent regex builder search the complete reconciled official and installed inventory before paging. The privileged regex worker has a 128 MiB memory limit, 500 ms per slice, a five-second total budget and two concurrent admission slots. Global/sticky expressions reset between records. Invalid or excessive expressions report an actionable failure instead of blocking the application thread.

Filters include installed/running/not-installed state, family, reported capability, exact published variant, reported quantization (including Unknown), maximum reported size and hardware-fit verdict. Sorts include name, size in both directions and reported context. Enumerated variants and quantizations come from actual records. Local-only installed tags remain visible. Quantization comes from reported local API metadata; tag names never supply guessed quantization or fit. Unknown sizes are excluded only when an explicit maximum-size filter is selected.

The current installed/running state is fetched from documented local APIs. A bounded durable installed snapshot retains local-only tags after restart or service failure. Stale snapshots are labeled by their last checked timestamp; state filters produce no matches when current local state cannot be verified. Official refresh age and identity remain visible. Complete official per-variant explanations and detailed metadata for uninstalled variants remain incomplete.

## Hardware evidence and downloads

Hardware collection reports actual CPU model, logical core count, architecture, total/free RAM and free disk for the detected Ollama model directory when available. An externally configured service can use another model directory. Supported fixed NVIDIA telemetry locations may supply GPU name, capacity and driver; Ollama backend compatibility remains Unknown. GPU capacity is never inferred from running-model usage or a model name.

Every fit verdict includes evidence and unknown fields. A blob larger than 90% of total RAM is conservatively Unlikely. Positive fit classifications require verified GPU/backend, exact parameter/quantization/KV/context information and disk evidence. Missing required evidence remains Unknown. Synthetic tests exercise all four classifications; catalog rows currently lack enough exact runtime metadata for reliable positive fit, which the UI exposes.

A batch contains exact tags only. Review shows reported byte estimates, conservative additional disk estimate, unknown sizes, fit evidence and aggregate known bytes. There is no price, payment, account or checkout. Pull concurrency is configurable from one to three. Per-item state and actual current-blob completed/total byte counts are durable. Interrupted pulls become queued on restart. Retry reconciles current installed tags and lets Ollama reuse content-addressed blobs. Completion requires both a success stream record and the exact installed tag. Partial/failed/cancelled outcomes stay explicit. No failed item removes an installed model.

## Chat

Saved sessions support local browsing, name search, rename, deletion with two acknowledgements and a confirmation slider, and explicit redacted export. New conversations use an actually installed model picker. System prompt, temperature, output-token limit and context-token limit are editable and bounded. Streaming updates are displayed, Stop aborts the request, Regenerate replaces the last user/assistant turn, and any received partial response is saved on cancellation or failure. The most recent 40 messages are sent; saved history is limited to 128 messages and 512,000 characters, with a 128,000-character response bound and one concurrent generation.

Assistant Markdown is sanitized into a scriptless opaque-origin frame. Links, external requests, images, forms and executable provider markup are blocked. The native image picker supplies opaque grants only; the renderer cannot submit file paths or image bytes. Sending rechecks source identity, decodes/re-encodes PNG/JPEG through the bounded worker and requires the installed model's documented `show` response to explicitly include `vision`. Inputs support at most four files, two million pixels per image and 4 MiB aggregate normalized PNG data per turn. Private copies use exclusive 0600 files and opaque IDs; saved history stores validated references with exact hashes. Active image context is bounded to 8 MiB and a session retains at most 16 images. Resumed context rereads bounded bytes and verifies hashes before invoking the local API. Regeneration reuses the original verified images. Deleting a conversation removes its private image copies; text exports include only names, types and sizes, never image content or private references.

Image selection itself is disabled until the current conversation model has verified installed `show` metadata explicitly reporting `vision`. The disabled state offers capability verification and an Installed models route, with the exact local-service or metadata failure. Evidence includes the checked model, timestamp, local source and digest when reported; changing sessions clears prior evidence. Sending still rechecks native metadata and source bytes independently of the renderer.

Incoming response content is checkpointed immediately and then at most once every 750 ms, with a final flush on success, cancellation or failure. Terminal status follows that flush. Restarted sessions retain the most recent checkpoint, although an abrupt crash can lose the final fraction of a second; interrupted streams are never marked completed. Attachment normalization and chat admission participate in lifecycle cancellation, and simultaneous generations fail closed. The tool tabs preserve their mounted components and unsent drafts when switching between regex, converters and models; parent workspace remount behavior requires separate lifecycle verification.

## Local model copy and standalone generation

Installed model cards offer a reviewed copy with a suggested collision-free explicit tag and a validated advanced destination field. Confirmation checks the installed source, refuses an existing destination and invokes only the documented local copy API. Successful empty HTTP 201 responses are accepted, then the exact destination is reconciled against installed tags before success is shown. This does not pull models; an external actor changing a tag concurrently remains outside the local API's available atomic preconditions.

The text generation section selects actual installed models and verifies their reported `completion` capability and context limit before enabling generation. The privileged boundary repeats those checks. Requests use the documented `/api/generate` streaming API with a fixed endpoint, rejected redirects, 16,000-character prompt/system bounds, 512–32,768 context tokens, at most 8,192 output tokens, a ten-minute stream deadline and a 128,000-character response bound. Chat and standalone generation share a single active-response admission boundary. Defaults explain temperature, output length and context memory costs.

Response records are private, atomic and checkpointed, with durable success/cancelled/failed outcomes. Prompt and system text are sent to the selected local model but never stored in generation history. After restart, an interrupted response becomes failed with its partial output preserved. Forty-item history pages contain summaries; selecting one rereads its bounded saved response. Explicitly selecting a response permits export through the shared format-aware exporter, with a content-review notice and no prompt inclusion. Cancellation and shutdown include admitted and active generation work. No actual inference is claimed by the synthetic fixtures.

## Local-service harness and recovery

Three shipped stopped-service profiles expose conservative (2048-token context), balanced (4096-token context) and runtime-default resource settings. The conservative preset admits one request and one loaded model with a short keep-alive; it reduces concurrent demand but cannot establish actual model fit. Preflight shows actual hardware evidence, exact approved executable digest/version, fixed `serve` arguments, local-only host, environment values, private working-directory purpose and required port. Model-specific fit remains Unknown until installed-model inspection; these service profiles do not load or download models.

A native semantic picker issues an opaque runtime review. Selection hashes a bounded regular ELF/PE file without executing it. This build has no known-release-digest or native publisher-signature attestation for the selected file, so the review explicitly states that path and version output do not establish an official publisher. The user must approve execution of the exact displayed SHA-256 bytes before a fixed `--version` probe runs, with five-second and 16 KiB output limits. Compatible platform headers, executable permissions, size, inode/device, timestamp and full byte hash bind registration. Every preflight and launch repeats that identity/hash validation. Scripts, links, incompatible platform files and unrelated version responses are refused. Native paths remain private, unrelated environment values are stripped and no arbitrary arguments or shell text cross the bridge.

Confirmed launch retains the stopped-profile snapshot and readiness checks. Restore requests termination of only the owned process, waits for its close event and uses a bounded escalation if needed. A failure to verify closure is reported explicitly and ownership remains active. Failed readiness verifies closure before reporting stopped-state restoration. Complete configuration snapshot/restore remains pending. Launch never installs software, downloads models or modifies an external service configuration.

Additional non-Ollama harness schemas, vendor signature/release-digest attestation, native Windows process restoration proof, model-specific launch profiles and complete configuration snapshot/restore remain incomplete. Explicit digest trust is recorded as user-reviewed execution, never official provenance. A process launch is never presented as an Ollama API capability. The offline troubleshooter remains usable alongside saved chat and last verified catalog, with platform-specific recovery steps and a path back to service verification.

## Verification boundaries

The tests use synthetic protocol streams and temporary app-owned files. They verify multi-page catalog/tag completeness and offline retention, response identity, fit uncertainty, pull progress and installed-state reconciliation, streamed chat and generation persistence/cancellation, reviewed copy reconciliation, actual bundled PNG normalization with synthetic vision-capability protocol fixtures, changed-image rejection, regeneration and attachment secret exclusion, input allowlisting, full-inventory regex/filter/sort behavior, installed-only/offline reconciliation and regex termination/resource limits. `tests/ollama-workflows.browser.mjs` launches the actual built Electron application against an explicitly labeled loopback protocol fixture and exercises copy confirmation, capability-disabled/enabled image selection and streaming generation through native IPC. It verifies saved generated bytes and prompt exclusion, with zero page errors. These checks do not establish actual local model inference/download, Windows service launch, full localization, complete accessibility or packaged installer behavior.

The Linux native trust fixture compiles an explicitly synthetic owned ELF version responder, requires digest confirmation before execution, verifies its fixed version probe and refuses changed bytes, scripts and unrelated executables. It also verifies three semantic presets, unavailable-runtime preflight, fixed native launch failure, close-event verification and stopped-state restore. No model data or inference is involved. This fixture establishes control flow and native process execution, not an official Ollama installation or successful model inference.
