# Local access preferences, element locks, and authenticator

The shared presentation-mode record lives in the caller-selected shared OS application-data directory as `shared-ui-state.json`. Its selected display name, active state, revision, and encrypted credential verifier propagate through a directory watcher. Missing records start inactive; corrupt or unreadable records report unavailable and apply presentation suppression. The app shell must honor the chosen name, force English and omit language, humor, personal-vocabulary and hidden capability routes while active, and restore saved choices afterward. Other native applications must implement the same documented record and OS encryption context before cross-application interoperability can be claimed.

These are personal convenience locks. They are not encryption or a security boundary against someone using the OS account. The shared control can be reset by manually removing the displayed shared application-data record. Element locks and authenticator entries live in the separate stable application-local directory; deleting it also removes preferences, authenticator entries, local tickets and history. The app never deletes these folders through recovery.

`createSecurityService` requires an OS encrypted-storage adapter. Electron `safeStorage` must report encryption available and must not use `basic_text`. There is no plaintext fallback. PIN/password verifiers use independently salted scrypt hashes; TOTP uses standard RFC 6238 with a one-period skew window. Verifiers and secrets are encrypted before persistence and omitted from status, lock lists and ordinary metadata. Test adapters are fixtures only.

## Native integration

Call `registerTargets(nativeLockTargets(commands))` before renderer startup. `protectedLockIds(channel, action?, commandId?)` maps protected native operations to destination, action, command and tab identifiers. A native handler must call `assertUnlocked(ids)` immediately before the protected operation and `consumeSurfaceUnlock(id)` for each successful action target. Native callers choose these identifiers from the verified channel and command; renderer-supplied arrays never choose native permission targets. Dynamic renderer targets register with `security('lockRegister', {targets:[{id,label}]})`; they cannot supply ancestors or overwrite pre-registered native targets. Callers may register native ancestor relationships themselves. IDs accept bounded letters, digits, colon, dot, underscore and hyphen.

Each element has independent credentials and one of six policies: PIN, password, PIN plus password, password plus TOTP, PIN plus TOTP, or password plus PIN plus TOTP. Every required factor must match in one bounded attempt. PIN accepts 4–12 digits. Creating/changing a lock requires acknowledgment of the disclosure; existing lock changes require all current factors. OTP lock pairing accepts a standard URI and arms only after confirmation with a current code. Unlocks last for one action, 1–1440 minutes, or until the app closes. They start locked after restart. Explicit `lockAgain` clears a session, and `lockRemove` requires the existing factors.

`attachSecurityControls(root)` installs the renderer interception layer. Elements expose stable `data-lock-id` values; `mg-lock-request` opens the anchored wizard with `{id,label,element,configure}`. It intercepts pointer activation, keyboard activation, changes, text editing and drag activation on locked composed event paths, marks `aria-disabled`, and preserves an operable unlock target. The app's context menus, shortcuts and programmatic handlers must use this same layer and native guard. This module's existence alone does not prove every surface has been wired. Manual PIN and keypad entry share one validator and attempt budget. The current implementation submits all factors together and names their required order; it does not implement progressive step-by-step factor screens.

Five failed attempts begin an exponentially escalating wait, capped at 30 minutes. Local waiting games only clear the wait and restore the same five attempts as serving the clock; they never authenticate or grant a lock session. The rolling-hour skip budget is shared across local lock budgets and allows three clears. Single-use, expiring challenges are generated and graded in the main process. School mode starts at ten sums. Five failed dish questions progress to sums, a failed sums round progresses to a nine-cell timed mole game, and a lost timed round leaves the clock. Mole hits are graded at receipt against the actual main-process clock and schedule, counted once, and completion cannot succeed early. The dish rung currently presents text questions; photographic identification is not implemented.

## Local recovery

`mg-recovery-tickets` creates, lists and advances fictional local tickets. Its fixed disclosure states: “Nothing is sent anywhere. Tickets exist only on this machine. No network request is made, no data is collected, and nobody is reading them.” Resolution explains manual reset and opens the exact displayed application-data folder through an injected native file-manager callback. Missing or failed integration reports an error. Nothing performs deletion. Unlock prompts emit `recovery-request`; Help and lock settings should route to this same component. Ticket export, bulk management and localization remain work for the containing application.

## Authenticator

Standard URI enrollment preserves SHA-1, SHA-256 or SHA-512, six through eight digits and a bounded 1–86,400-second period. URI validation rejects HOTP, duplicate/unknown parameters, conflicting issuers and malformed values. Generated pairing uses cryptographic randomness, and the renderer draws the QR in process using the installed `qrcode` package. Explicit reveal shows the one-time QR and grouped manual secret. No QR web service, network call or secret file is used. A correct current code confirms enrollment before persistence; stored secrets are never revealed afterward.

Entries show current codes, next codes and numerical rollover countdowns. The system clock's accuracy is explicitly unverified. Search uses the adjacent regex builder, and removal requires inline confirmation. Enrollment and removal call the optional native `recordMutation(action, redactedMetadata)` hook before reporting success; the containing application must supply its append-only local-history integration. This module does not supply a protected history manager. URI/generation enrollment is implemented; camera/image/clipboard QR scanning, manual parameter forms, grouping, reorder/bulk management and deliberate secret export are not implemented here.

## Verification limits

Focused native fixture tests cover RFC vectors, TOTP skew, encrypted persistence, vault refusal, shared rename propagation, corruption, all six policies, independent sessions, expiry, ancestor refusal, immutable registration, ladder replay/expiry/budget/escalation, main-timed hits, approved-host origins and recovery folder parity. `node tests/security-controls.browser.mjs` runs genuine Material components in isolated Chromium and exercises interception, the PIN keypad, policy controls, token consent and local recovery. It uses mocked bridges, not real credentials or native mutations. This establishes component interaction, not full application integration, external authenticator scanning, screen-reader verification, cross-application interoperability or packaged Windows evidence.
