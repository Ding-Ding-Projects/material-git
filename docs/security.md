# Local access preferences and authenticator

`createSecurityService({directory, authenticatorDirectory, vault})` manages a shared local presentation-mode record and a separate application-local authenticator cache. The caller passes a shared OS application-data directory shared by participating applications, not the per-application Electron `userData` directory. The version-1 record is `shared-ui-state.json` with `schoolMode: {displayName, active, revision, updatedAt}`, an encrypted scrypt credential verifier, and encrypted per-element verifiers. The repository did not establish a pre-existing desktop shared-record format; other applications must implement this documented format and share the same OS encryption context before interoperability can be claimed. A browser preference record is not interchangeable with this native store.

The service watches the containing directory so atomic replacements propagate to subscribed running applications. Missing records start with an inactive default mode; malformed or unreadable records report unavailable with presentation suppression active. Watch failures are reported explicitly. Credential setup, credential verification, mode activation/deactivation, and renaming use a shared in-process attempt budget of five failed attempts followed by thirty seconds. Stored PIN/password verifiers use scrypt with independent random salts. Enabling and disabling the mode requires the current credential; changing an existing credential requires its previous value. The rename is persisted and emitted without exposing the shipped name in the active control.

Secret storage requires an adapter for Electron `safeStorage`; `isEncryptionAvailable()` must be true and the selected backend must not be `basic_text`. There is no plaintext fallback. Ciphertexts are stored under private application-data directories; secret values and verifier material are omitted from status, lists, history and ordinary exports. Linux installations without a supported keyring cannot save secrets. Vault ciphertext is protected by the OS account and is not a claim of stronger security against someone who already has that account.

The mode and per-element locks are personal convenience locks, not security boundaries. Recovery is manual deletion of the displayed shared application-data record; this resets participating applications' shared mode and credential. The service implements `lockSet` and `lockVerify` groundwork only. Disabled-action interception, timed unlock sessions, factor combinations, protected history, support-ticket recovery flows, and the unlock ladder are not implemented by this module. No consumer should claim those flows work from the existence of a credential verifier.

The authenticator supports standard RFC 6238 TOTP over SHA-1, SHA-256 or SHA-512, six through eight digits, and a bounded 1–86,400 second period. URI enrollment preserves declared parameters and rejects unsupported HOTP, duplicate parameters, conflicting issuer labels and invalid values. Pairing generation uses local cryptographic randomness; QR encoding uses the installed `qrcode` package in process, with dark modules on a light background and a quiet zone. An explicit reveal shows the one-time pairing QR and grouped manual secret; no QR service, network call, file write or ordinary export is used. A correct current code within one period of clock skew is required before enrollment is persisted. Stored secrets are never revealed later.

Entries show live current codes, next codes, a numerical rollover countdown, and a local clipboard copy action. The system clock is used; its accuracy is explicitly unverified. Deletion requires inline confirmation. Searches use their own adjacent regex builder. Entries survive restart through OS-encrypted local storage. Missing or invalid encrypted storage fails visibly.

Current limitations: enrollment supports pasted standard URIs and generated local pairings; QR image/clipboard decoding, camera scanning, manual parameter form, reordering, groups, bulk management, QR decoding proof against a real external authenticator, clock synchronization, deliberate secret export, mutation-history repositories and protected history-manager UI remain unimplemented. Tests validate published RFC vectors, skew boundaries, parameters, credential attempts, vault refusal, encrypted persistence and restart metadata. They do not establish interactive, accessibility, QR-scanning, cross-application or packaged-runtime evidence.

The renderer component is `mg-security`. It uses bridge actions `status`, `setCredential`, `verifyCredential`, `rename`, `setMode`, `pairingGenerate`, `authenticatorList`, `authenticatorEnroll`, `authenticatorCodes`, `authenticatorRemove`, `lockSet`, and `lockVerify`. `onSecurity` subscribes to status updates, and `security-change` bubbles updated status to the app shell. The shell must apply the mode live, force English narration/presentation, omit language/playfulness/vocabulary controls and hidden capability routes, and restore prior stored choices when it turns off. `mg-settings.schoolMode` handles omission of its own presentation controls without overwriting stored choices.
