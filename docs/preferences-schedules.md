# Scheduled preferences and approved sources

Settings has General, Appearance, Voice and sound, Attention preferences, Personal vocabulary and Scheduled settings tabs. Search looks across tabs and each setting has an explanation, its actual compiled value or saved-record provenance, and an independent reset. The visible application name does not change package identity, application-data paths, update feeds or diagnostic identity.

Scheduled settings use schema version 1, a configured IANA timezone and at most 64 rules in a 256 KiB document. Each rule has a stable identifier, label, enabled flag, integer priority, optional inclusive calendar start/end dates, start/end wall times, one or more weekdays and validated settings. Every day is one rule containing seven weekdays. Start is inclusive and end exclusive; equal times cover the full day. Overnight windows belong to their starting date and weekday. Repeated daylight-saving wall times match twice; skipped times never occur. Higher priority wins; equal priorities sort by stable identifier using code-unit order. When an override ends, the unchanged local base reappears.

The guided editor can select any persisted setting and save an element’s existing local appearance snapshot as an override. Local rules apply those values directly. HTTPS rules read `{ "schemaVersion": 1, "settings": { "theme": "dark" } }`, optionally with an `appearance` map of stable element identifiers to appearance records. Home Assistant rules read a `binary_sensor` or `input_boolean` entity: `on` applies the local rule values, `off` yields to other matching rules or base settings. Unknown entity states do not apply.

A source must be approved through the connection interface before a rule can reference it. The production route requires HTTPS, a public DNS name, no embedded credentials, no fragments and the default TLS port. The main process rejects private/reserved DNS answers, pins a validated address for each TLS request, refuses redirects and accepts only JSON. Requests are read-only GETs. Sources refresh on activation and at a saved interval of 30–3600 seconds. Responses are limited to 64 KiB and eight seconds, duplicate JSON keys and unsafe keys are rejected, and old generations cannot replace a newer configuration. A failed or offline source returns to local/base settings and reports a recoverable warning; remote responses never become saved base preferences.

Access tokens are encrypted through the operating system credential facility under stable connection identifiers. The interface displays only whether a credential is stored. Tokens are never returned to the renderer or put in rule files, exports or history. Credential saving is refused if the operating system cannot provide protected storage. Public settings exports omit personal-vocabulary contents and file metadata as well as source credentials. Imported sources must match existing approved connections; importing a file cannot approve a new network destination.

Settings JSON import validates the whole document before application. The base preferences, schedule rules and element styles are exported together. If a native write fails during import, previous base and schedule values are restored through the same validated APIs. A process crash between these writes is not a cross-file transaction; check local history and re-import the previous export if recovery is needed.

Focused tests: `tests/preferences-advanced.test.ts`, `tests/settings-inventory.test.ts`, and the built desktop interaction route `node tests/preferences.browser.mjs`. The latter uses a temporary application profile, exercises real native settings persistence and controls, and writes screenshots plus a payload-free receipt to its printed temporary directory. External read-only source boundaries use deterministic injected transport tests; these do not prove a real external Home Assistant installation.
