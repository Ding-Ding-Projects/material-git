The desktop exposes provider tasks through `window.material.github(action, payload)`. `GitHubService` owns an explicit action allowlist, validates repository and entity identifiers, selects a registered hostname, constructs main-process CLI arguments, and returns bounded provider results. The interface does not accept a URL, executable, shell command or custom authentication header. Its internal action identifiers select task behavior; they are not a user-facing command catalogue.

List and detail actions cover repositories, issues, pull requests, Actions, releases, Projects v2, discussions, search, repository security, organizations, gists and Codespaces. REST pages follow actual Link headers. Project and discussion pages use provider-issued GraphQL cursors; a subsequent page cannot invent a cursor or skip the previous page. Some search fields filter only the current provider page, and the response says so. Issues exclude pull requests without erasing the source page’s continuation. API errors, GraphQL errors, bounded-result failures and rejected merge results remain failures.

Real entity pickers provide labels, assignees, collaborators, reviewers, milestones, branches, tags, workflows, project identities and discussion categories. Every response retains provider fields while supplying normalized title, subtitle, URL and task identifiers. Issue, pull-request and discussion task identifiers are their numbers; Codespaces use names; organizations use login handles; releases, Projects v2 and gists retain their provider identifiers. Choice rows expose semantic `value` and `label` where the destination accepts a name or number.

Supported mutations currently include repository create/edit/delete/fork; issue create/edit/comment/close/reopen; pull-request create/edit/comment/close/reopen/merge/review/reviewer requests; run cancel/rerun/rerun-failed/delete, workflow dispatch/enable/disable and artifact download; release create/edit/delete/upload/download; project create/edit/delete/add issue-or-PR item; discussion create/comment/close/reopen; gist create/edit/delete; Codespace create/start/stop/delete; alert dismissal; and organization invitation/member removal. Uploads select regular files within the approved workspace, at most twenty assets of 256 MiB each. Nested provider input is serialized into a bounded private JSON request file, removed after execution. Project item URLs must name an issue or pull request on the selected registered forge.

A direct mutation request prepares a review and never writes, including when its payload says `confirmed: true`. The desktop renders `response.review`, then invokes `github('apply', {reviewId, confirmed:true})`. The main process stores an exact cloned action, target, fields, hostname and verified account. Reviews expire after five minutes, are single use, reject replacement arguments, and reject an account change. Unknown fields and malformed input fail before writes. Applying a successful mutation returns a reload notice; a merge followed by unsuccessful source-branch deletion reports the partial outcome. Browser task state never supplies authentication headers or stored credentials.

Enterprise hosting uses the constructor’s `resolveHost` registry callback and an asynchronous request context, keeping simultaneous requests and reviews bound to their selected forge. Without that callback only github.com is allowed. Secrets and known credential fields are redacted recursively and operation output uses the engine’s bounded streaming redaction. Actual CLI requests close stdin, disable prompts and report real exit status. Credential and scope failures are returned for the desktop’s in-context account recovery route.

The contextual task registry adds 93 registered helpers for labels; Actions caches; repository deployment keys; account SSH and GPG keys; secrets and variables; rulesets and attestations; agent tasks and skills; richer issue relationships and attachments; pull-request properties/checks/diff/readiness; repository file reading and settings; and project field/item management. Each helper uses the pinned CLI option and argument schema, a human task title, and main-process argument preparation. The `mg-github-task` component provides described controls, repeated values, searchable finite choices, native file/directory selection, actual paged entity pickers, and exact server review/apply. Its automatic browsing mode reads only non-mutating tasks whose required inputs are already supplied. Optional task settings collapse after a successful read; records render as Material lists with expandable details. Destructive tasks require two acknowledgments and a confirmation slider. Installation/update of third-party skills explicitly warns about external code. No third-party code is installed or executed in agent verification.

Additional picker sources include existing secret/variable names, environments, deployment keys, account keys, rulesets, project fields/items, repositories and organizations. Users may enter a new valid name where creation requires one. The selected issue, pull request, run, gist or Codespace cannot be silently replaced through task arguments. Project graph identities are resolved to their real CLI project number and owner. File inputs and destinations must stay within the approved workspace; path checks reject symlink escapes. Native confirmation flags are inserted only in reviewed mutation preparations. A file read with a selected output path prepares a review rather than silently writing. Skill update is correctly modeled as a mutation.

Native CLI list limits are explicit. Increasing the limit or narrowing filters reads further records; a bounded CLI result does not prove that the provider has no more records. The component’s loaded-record pagination is separate from source pagination. Rich field controls do not establish unrestricted parity for browser/editor helper launches, native interactive prompts or terminal sessions, extra option combinations requiring provider privileges, binary preview formats, or every remote platform. Those cases must retain their real availability and provider errors. Clone/sync/checkout/revert are delegated to the separate native Git workbench. Full feature mapping and actual domain mounting are maintained by their owners; registration alone is not proof of graphical integration.

Verification covers fixed endpoint/task boundaries, source pagination, entity choice semantics, exact reviews, replay and target replacement rejection, account changes, GraphQL errors/cursors, merge refusal, security filter semantics and hostname registration. A real read-only request through this service returned the official cli/cli repository and its trunk default branch. No live mutation was performed. Native Windows, graphical domain integration and destructive-provider outcomes still require their own evidence.

The native service owns a private process engine with no generic operation-history or renderer stream subscription. API bodies are parsed and recursively sanitized before crossing the domain bridge, preventing arbitrary secret-scanning values in raw JSON from entering the generic history. The constructor accepts authorization callbacks before each request and before applying the exact stored action/target; its completion callback receives only the successful bound mutation. The hosting application tracks asynchronous activity and calls close() on shutdown to cancel native process trees.

Reviews now prepare the entire REST body, GraphQL mutation, or native argument vector before issuing the review ID. Target numbers, enum choices, owner/account lookups, repository-to-ID resolution, source issue/PR URLs, workflow inputs and native path constraints are validated during that read-only preparation. Apply re-prepares without writes and rejects a changed request or provider identity. Target snapshots include repository/entity IDs, source branch identity, release tag and selected upload-file metadata; the mutation executes the exact stored prepared request. The renderer can inspect the sanitized prepared request through review.prepared. Upload-file metadata checks do not establish cryptographic immutability of large binary files; that remains a narrower guarantee than the alias-import snapshot.

Its host owns route navigation and reload. Account recovery opens the actual account component.
