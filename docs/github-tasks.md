The desktop exposes provider tasks through `window.material.github(action, payload)`. `GitHubService` owns an explicit action allowlist, validates repository and entity identifiers, selects a registered hostname, constructs main-process CLI arguments, and returns bounded provider results. The interface does not accept a URL, executable, shell command or custom authentication header. Its internal action identifiers select task behavior; they are not a user-facing command catalogue.

List and detail actions cover repositories, issues, pull requests, Actions, releases, Projects v2, discussions, search, repository security, organizations, gists and Codespaces. REST pages follow actual Link headers. Project and discussion pages use provider-issued GraphQL cursors; a subsequent page cannot invent a cursor or skip the previous page. Some search fields filter only the current provider page, and the response says so. Issues exclude pull requests without erasing the source page’s continuation. API errors, GraphQL errors, bounded-result failures and rejected merge results remain failures.

Real entity pickers provide labels, assignees, collaborators, reviewers, milestones, branches, tags, workflows, project identities and discussion categories. Every response retains provider fields while supplying normalized title, subtitle, URL and task identifiers. Issue, pull-request and discussion task identifiers are their numbers; Codespaces use names; organizations use login handles; releases, Projects v2 and gists retain their provider identifiers. Choice rows expose semantic `value` and `label` where the destination accepts a name or number.

Supported mutations currently include repository create/edit/delete/fork; issue create/edit/comment/close/reopen; pull-request create/edit/comment/close/reopen/merge/review/reviewer requests; run cancel/rerun/rerun-failed/delete; release create/edit/delete/upload; project create/edit/delete/add issue-or-PR item; discussion create/comment/close/reopen; gist create/edit/delete; Codespace create/start/stop/delete; alert dismissal; and organization invitation/member removal. Uploads select regular files within the approved workspace, at most twenty assets of 256 MiB each. Nested provider input is serialized into a bounded private JSON request file, removed after execution. Project item URLs must name an issue or pull request on the selected registered forge.

A direct mutation request prepares a review and never writes, including when its payload says `confirmed: true`. The desktop renders `response.review`, then invokes `github('apply', {reviewId, confirmed:true})`. The main process stores an exact cloned action, target, fields, hostname and verified account. Reviews expire after five minutes, are single use, reject replacement arguments, and reject an account change. Unknown fields and malformed input fail before writes. Applying a successful mutation returns a reload notice; a merge followed by unsuccessful source-branch deletion reports the partial outcome. Browser task state never supplies authentication headers or stored credentials.

Enterprise hosting uses the constructor’s `resolveHost` registry callback and an asynchronous request context, keeping simultaneous requests and reviews bound to their selected forge. Without that callback only github.com is allowed. Secrets and known credential fields are redacted recursively and operation output uses the engine’s bounded streaming redaction. Actual CLI requests close stdin, disable prompts and report real exit status. Credential and scope failures are returned for the desktop’s in-context account recovery route.

These adapters do not establish all GitHub CLI capabilities as complete. Native clone/sync/checkout/revert, workflow dispatch and enable/disable, cache management, logs and binary downloads, full project field/item management, secret/variable/key/ruleset/attestation/agent/skill families, richer issue relationships/attachments, and interactive terminal sessions require additional task adapters and renderer controls. The ordinary structured runner already owns many corresponding CLI definitions; defining them in a catalogue does not establish native-task GUI parity. Codespace port selection and copying use the separate Cloud workspaces adapter. Full feature mapping is maintained separately by the application coverage owner.

Verification covers fixed endpoint/task boundaries, source pagination, entity choice semantics, exact reviews, replay and target replacement rejection, account changes, GraphQL errors/cursors, merge refusal, security filter semantics and hostname registration. A real read-only request through this service returned the official cli/cli repository and its trunk default branch. No live mutation was performed. Native Windows, graphical domain integration and destructive-provider outcomes still require their own evidence.
