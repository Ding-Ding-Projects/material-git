# Local authenticator entries and protected backups

The Local access workspace contains the app's native TOTP authenticator. Registered entries keep exact issuer/account, SHA1/SHA256/SHA512, six to eight digits and their chosen 1–86,400-second period. Each entry also has a editable display label, a registered local icon and an optional named group. Create or rename groups, change entry labels/icons/groups, move matching selected entries in bulk, and reorder the complete saved entry list with keyboard-operable up/down controls. These changes keep the stable entry ID and encrypted secret intact. Legacy version 1 entries acquire safe metadata defaults when read and migrate on the next successful mutation.

Search uses an independent text/regex control with the adjacent builder. Group filtering composes with search, pagination shows twenty entries, and selection supports page, all matches, inverse, clear and Shift ranges. Hidden selections remain selected and are excluded from filtered actions. Ordinary export uses the actual datum's formats and includes labels, group names/icons and TOTP parameters; it explicitly omits secrets, codes and encrypted vault blobs. It cannot restore a secret.

Registration accepts a standard `otpauth://totp/` URI or grouped manual base32 with issuer/account, algorithm, digit count and period. URI parameters are preserved. File and clipboard image routes use native callbacks and accept no renderer-supplied paths; unavailable integration stays disabled with an explanation. They read at most 8 MiB, while the native image adapter validates image headers and tighter pixel bounds before local jsQR decoding. Exactly one readable, valid TOTP pairing is required. Nothing is enrolled until its current code matches. Wrong codes and invalid base32 cannot save an entry.

A camera route is available only when the runtime exposes media capture and the native app supplies a one-use, own-renderer, video-only permission handshake. The user starts scanning explicitly; denial is reported. Decode frames remain local and bounded. Stop, a hidden owning workspace, page visibility loss and component removal stop all tracks. No global permission grant is implied by this component.

An explicit one-time reveal draws the QR locally with a quiet zone and dark-on-white contrast, shows grouped manual base32 and exact parameters, and gives the QR a meaningful text alternative. Changing a pending pairing clears its reveal; registration or explicit discard clears it from memory. Stored secrets are never revealed. Current codes announce on rollover, while the ordinary textual countdown updates each second without a repeating live announcement. Next-code preview and code copying are explicit. The app states that the system clock is not externally verified; check the device time when a provider rejects a code.

Removal requires a native one-use review of the exact entry IDs, two independently operated keys and a full confirmation slider. One key cannot enable the slider, partial progress cannot apply, and Emergency exit/Escape revoke the review and restore focus. Progress and completion are visible without blocking interaction; reduced motion disables animation. Native state changes, expired receipts and attempts to use an export review for removal reject. A removed entry requires re-enrollment or a compatible protected restore.

Protected backup export is a separately named action behind the same scope review and gate. A separate 12–256-character backup password seals all parameters, secrets, labels and groups with AES-256-GCM and bounded scrypt; random salt/IV and the authenticated schema/version prevent unsafe format changes. Only a strict ciphertext envelope reaches the exclusive native-picked file writer. Neither the password nor plaintext backup crosses the ordinary export bridge or enters history. Loss of the password makes the backup unrecoverable. Protected import uses a native-picked encrypted file and that separate password. Strict envelope, KDF, size and authenticated contents validation runs before review. Choose to skip or replace exact issuer/account duplicates; the review shows each add/skip/replace decision, prior public parameters when replacing, native-generated destination IDs and groups. Ambiguous multiple local duplicates require cleanup first. Cancellation, wrong passwords, stale receipts and incomplete gates preserve live data. Import decrypts and rewraps secrets only in the native issuer; it returns no stored secret. Existing IDs survive replacement; unrelated entries remain unchanged.

Every native authenticator action rechecks its fixed registered security destination/action locks. Review issuance preserves a one-use unlock; an attempted mutation/save consumes it. Review cancellation remains reachable under locks. Writes use the existing OS-vault encryption with no plaintext/basic-text fallback and atomic local replacement. Mutation callbacks contain redacted metadata. A separately protected encrypted mutation-history manager remains a following integration batch; ordinary managed history is not that manager.

Verification: `tests/authenticator-import.test.ts` and `tests/authenticator-import-render.test.ts` cover authenticated native import, duplicate policies, exact immutable scope, cancel/stale/locked receipts, hostile contents, restart and the actual Material keyboard gate. `tests/authenticator-management.test.ts` uses isolated encrypted-vault fixtures and actual local PNG-to-jsQR decoding to exercise restart, edit/group/order/bulk scope, redacted output, exact gates, expiry/staleness, protected backup authentication and real one-use locks. `tests/authenticator-render.test.ts` bundles real registered Material controls and drives native manual enrollment, labels/groups, redacted export, cancel/full removal and three language modes. Existing RFC 6238 tests cover SHA1/SHA256/SHA512. These checks do not certify Windows vault/installer behavior, physical camera permission or external account acceptance.
