# Startup dim sum

Material Git makes one fresh 10% draw per native launch. Winning launches choose one dish from the official public catalog. The app becomes usable independently of this background work. The card dismisses after seven seconds or with its Material Dismiss button or Escape, never takes focus, and disappears when the user interacts with another part of the app.

First runs, active tasks or drafts, errors, updates, the shared presentation mode, quiet narration and low stimulation suppress the card. Suppression consumes that startup opportunity; ending a task or unlocking presentation mode cannot trigger a delayed card. There is no persistent off switch. Reduced motion receives a static card with no entrance or exit animation.

English, Cantonese and bilingual modes always show both catalog names exactly as `name.en` and `name.zhHant` record them. Cantonese puts the Cantonese name first; English and bilingual modes put the English name first. Funny levels style the surrounding introduction. They never rename the dish. Images have an accessible name containing both visible dish names. Missing photos receive localized factual status instead of a replacement image. Missing status means no matching photo was resolved from the bounded public release response; it does not claim an exhaustive audit of all historical releases.

## Official source and cache

The sole metadata authority is [Ding-Ding-Projects/dim-sum-photos catalog/index.json](https://raw.githubusercontent.com/Ding-Ding-Projects/dim-sum-photos/main/catalog/index.json). Photos must be individually published PNG assets in that repository's `catalog-v1*` releases and carry a SHA-256 digest in the public release API response. Desktop installer releases and unrelated image URLs are rejected. No photos or copied catalog are tracked in this repository.

The native process reads the fixed catalog and public release endpoints. Transfers have a shared twelve-second deadline, explicit byte limits and restricted redirects to GitHub's release asset hosts. Photos require matching size and SHA-256, PNG signature, bounded dimensions and successful CRC-checked decoding. The renderer receives verified bytes as a `data:image/png` value, so it makes no remote image request and requires no broader content security policy. The IPC takes no URL or other renderer parameter and must retain the app's trusted-frame validation.

Application data holds one sanitized metadata document of at most 2 MiB and one verified photo of at most 8 MiB. Metadata records the original source URL, catalog-content SHA-256 revision and fetch time. It refreshes after one day, retaining the last validated metadata when offline. A previously cached photo may display offline if the next dish draw selects it. Other offline photos are omitted with a truthful unavailable status. Temporary atomic-write files can briefly double their individual file's storage; failed writes remove them, and the next launch removes recognized interrupted transfers.

## Integration contract

Create one `StartupPersonalizationService` per native process after profile, security and effective preference initialization. Its application-data directory is `path.join(app.getPath('userData'), 'startup-personalization')`. Supply `fetch: (url, init) => net.fetch(url, init)` using Electron's network implementation, retaining manual redirect handling. Supply a live synchronous `context` callback for `firstRun`, `busy`, `error`, `updating`, `schoolMode` and `quiet`. Capture first-run state before creating a durable launch marker; unchanged preferences alone are insufficient to identify returning users. Maintain a security snapshot from `security.start()` / `security.subscribe()` rather than calling its asynchronous `status()` inside the callback. Read active operations, account changes, local jobs, update state and effective quiet preferences at each callback.

Extend `MaterialBridge` with the shared `StartupBridge` interface. Preload exposes `startupPersonalization: () => ipcRenderer.invoke('material:startup-personalization')`. Register the native handler through the existing trusted-frame `handle` wrapper, reject any supplied arguments, and return `service.startup()`.

Import the renderer module into the app and mount `<mg-startup-personalization>` once bootstrap, security and update state are resolved. Set `ready` to true on that first stable result and supply `settings` and `context` as Lit property bindings. Keep the element mounted so it retains its consumed opportunity. The renderer context must also include dirty drafts, open task dialogs and interactive flows in `busy`. The shared-mode flag must be fail-closed while security is unresolved. Context changes remove any visible card immediately. Do not await the card as part of app startup.

## Verification limits

`tests/startup-personalization.test.ts` exercises draw boundaries, suppression, metadata provenance, restricted transfers, cache bounds, offline metadata, corrupt photos and directory symlinks. `tests/startup-personalization.browser.mjs` compiles the actual registered Material composition and exercises language modes, focus, keyboard dismissal, missing-image status, narrow sizing, changed context, cancellation and auto-dismiss in isolated Chromium. Its fixture bridge provides component evidence; it does not establish installed-app IPC, Windows installer behavior or OS secure storage. Root integration and the final built application need their own verification. The Windows `build.bat` and `build-installer.bat` entrypoints cannot run on a Linux host without PowerShell/Windows support.
